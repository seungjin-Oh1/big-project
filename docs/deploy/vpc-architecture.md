# AWS 배포 아키텍처 (VPC 설계)

기술코치 답변을 반영한 설계다. 코치가 물은 세 가지 — **서브넷을 어떻게 쓸 것인가,
가용영역을 어떻게 배치할 것인가, 보안영역을 어떻게 나눌 것인가** — 에 답하는 것이
이 문서의 목적이다.

실행 절차는 [README.md](README.md), 환경변수는 [environment.md](environment.md)에 있다.

## 코치 답변과 그에 따른 결정

| 질문 | 코치 답변 | 이 설계의 반영 |
|---|---|---|
| EC2 한 대 vs 서비스별 분리 | 분리해야 한다. 보안·관리 차원. VPC 서브넷 수준으로 | 웹 계층 / 앱 계층 / 데이터 계층 3단 분리 |
| nginx vs API Gateway | nginx로 충분. API GW는 요청 횟수 제한·인증 통합·외부 파트너 제공이 필요할 때 | nginx 사용. API GW 미도입 |
| 컨테이너가 필요한가 | 단일 서버·단순 의존성·수동 배포로 충분하면 불필요. 이 프로젝트는 서비스가 많고 업데이트 잦아 필요 | Docker Compose 유지 |
| 실시간 통화 서버 분리 | 비용상 무리. 같은 서버에서 컨테이너만 분리 | stt-mask-api-modal을 앱 서버의 별도 컨테이너로 |
| VPC 필요한가 | 필요하다. 서브넷 3개 이상. 퍼블릭 1(로드밸런서, 처음부터는 X), 프라이빗 2(DB·백엔드). S3는 VPC 밖 | 아래 설계 |

## 1. 서브넷을 어떻게 쓰는가

서브넷 **5개**다. 코치가 말한 "3개 이상"을 넘기려는 게 아니라, 각각 있어야 할 이유가 있다.

| 서브넷 | CIDR | AZ | 무엇이 들어가나 | 왜 여기인가 |
|---|---|---|---|---|
| `public-a` | 10.0.1.0/24 | 2a | nginx, NAT Gateway | 인터넷에서 직접 닿아야 하는 유일한 계층 |
| `public-c` | 10.0.2.0/24 | 2c | (비움) | ALB는 최소 2개 AZ의 퍼블릭 서브넷을 요구한다. 나중에 붙일 자리를 미리 확보 |
| `private-app-a` | 10.0.11.0/24 | 2a | 앱 서버 (컨테이너 3개) | 인터넷에서 못 닿아야 한다. nginx를 통해서만 |
| `private-db-a` | 10.0.21.0/24 | 2a | RDS | 앱에서만 닿아야 한다 |
| `private-db-c` | 10.0.22.0/24 | 2c | (RDS 대기) | **RDS 서브넷 그룹은 2개 AZ를 강제한다.** Single-AZ로 띄워도 이 서브넷이 있어야 생성이 된다 |

**앱과 DB의 프라이빗 서브넷을 나눈 이유** — 계층이 다르면 보안그룹과 라우팅을 따로
걸 수 있다. 같은 서브넷에 두면 "앱 서버가 뚫렸을 때 DB로 못 가게" 만드는 통제가
보안그룹 하나에만 의존하게 된다.

## 2. 가용영역을 어떻게 배치하는가

**지금은 실질적으로 2a 한 곳에서 돈다.** 2c는 확장 자리다. 이유가 있다.

- **앱 서버를 여러 AZ에 둘 수 없다.** core-api가 통화 세션(`CallRegistry`), 오디오
  티켓, 로그인 실패 횟수, 캡차를 **메모리**에 들고 있고 ai-api의 Chroma는 **로컬
  파일**이다. 인스턴스를 늘리면 통화가 엉뚱한 서버로 붙고, 방금 받은 캡차가
  "틀렸다"고 나온다. 늘리려면 그 상태들을 먼저 ElastiCache(Redis)로 빼야 한다.
- **RDS만 2c 자리를 미리 잡아둔다.** 서브넷 그룹이 어차피 2개 AZ를 요구하고, 나중에
  Multi-AZ로 올릴 때 서브넷을 새로 만들 필요가 없다.

즉 **"지금은 단일 AZ, 확장 경로는 열어둔 상태"** 이고, 이게 이 프로젝트 규모에서
정직한 선택이다. 가용성이 필요해지는 시점은 상태를 외부로 뺀 다음이다.

## 3. 보안영역을 어떻게 나누는가

보안그룹을 **CIDR이 아니라 서로를 참조**하게 만든다. IP를 적으면 인스턴스를 바꿀 때마다
따라 고쳐야 하고, 실수로 넓게 열기 쉽다.

| 보안그룹 | 인바운드 | 소스 | 아웃바운드 |
|---|---|---|---|
| `sg-web` | 80, 443 | `0.0.0.0/0` | 전체 |
| | 22 | **내 사무실 IP만** | |
| `sg-app` | 8080 | **`sg-web`** | 전체 (NAT 경유) |
| | 9000 | **`sg-web`** | |
| `sg-db` | 5432 | **`sg-app`** | 없음 |

**여기서 지켜지는 것**

- 인터넷 → 앱 서버 **직접 접근 불가**. `sg-app`의 소스가 `sg-web`뿐이다.
- 인터넷 → DB **직접 접근 불가**. `sg-db`의 소스가 `sg-app`뿐이다.
- nginx가 뚫려도 DB에는 못 간다. `sg-db`가 `sg-web`을 허용하지 않는다.
- **8001(ai-api)은 어디에도 열지 않는다.** 같은 호스트의 컨테이너끼리는 도커 네트워크로
  통하므로 보안그룹에 뚫을 이유가 없다.

**이게 왜 중요한가** — ai-api와 stt-mask-api-modal에는 **인증이 아예 없다.** 8001이나
9000이 인터넷에 열리면 누구나 분석과 전사를 돌릴 수 있고, 상담 원문을 그대로 넣고
빼갈 수 있다. 이 설계에서 그걸 막는 것은 **애플리케이션 코드가 아니라 네트워크 통제**다.

### 예외 하나 — `/webhook`

Twilio가 전화 오디오를 밀어넣어야 해서 nginx가 이 경로 하나를 바깥에 뚫는다.
포트를 여는 게 아니라 nginx가 경로 단위로 9000에 넘긴다.

**여기에는 아직 인증이 없다.** Twilio 서명 검증(`X-Twilio-Signature`)이 구현되지 않아서,
주소를 아는 사람은 가짜 통화 세션을 만들 수 있다. **실제 상담 데이터를 넣기 전에
반드시 붙여야 한다.**

## 4. S3는 VPC 밖이다

코치 답변대로 S3는 VPC 안에 넣는 물건이 아니다. 다만 **Gateway Endpoint**를 걸면
프라이빗 서브넷에서 S3로 가는 트래픽이 **NAT를 타지 않는다.**

- Gateway Endpoint 자체는 **무료**다.
- 우리는 배포마다 RAG 자산 200MB를 받고, 상담 첨부파일이 계속 오간다. 이걸 NAT로
  태우면 데이터 처리 요금이 붙는다.

**꼭 넣을 것.** 안 넣어도 동작은 하지만 돈만 더 낸다.

## 5. 트래픽 흐름

```
① 브라우저 → 상담 화면
   인터넷 → IGW → nginx(public-a) → core-api(private-app-a) → RDS(private-db-a)

② 대면 녹음
   브라우저 → nginx /ws → core-api → (도커 네트워크) stt-modal → NAT → Modal A10G

③ 전화 상담
   Twilio → nginx /webhook → stt-modal → (도커 네트워크) core-api
                                       → NAT → Modal A10G

④ AI 분석
   core-api → (도커 네트워크) ai-api → NAT → OpenAI / Gemini
                                    → Gateway Endpoint → S3

⑤ 배포 시 자산 내려받기
   ai-api 기동 → Gateway Endpoint → S3 (deploy-assets/)
```

**②③④에서 컨테이너끼리는 도커 네트워크로 통한다.** 같은 호스트에 있으므로 VPC를
거치지 않고, 보안그룹도 필요 없다. 코치가 말한 "같은 서버에서 컨테이너만 분리"가
이것이다.

## 6. 비용

720시간(한 달) 내내 켜두는 기준이 아니라 **실제로 쓰는 시간** 기준으로 본다.

| 자원 | 시간당 | 40시간 사용 시 | 비고 |
|---|---|---|---|
| EC2 t3.xlarge (앱) | ~$0.21 | ~$8 | 정지하면 과금 0 |
| EC2 t3.small (nginx) | ~$0.03 | ~$1 | |
| NAT Gateway | ~$0.06 | ~$2 | **정지 불가. 끝나면 삭제할 것** |
| RDS db.t3.small | ~$0.04 | ~$2 | 7일까지 정지 가능 |
| EBS 60GB | — | ~$5/월 | **꺼도 과금** |
| S3 Gateway Endpoint | — | **무료** | |
| **합계** | | **약 $18** | |

**Modal A10G가 시간당 약 $1.1로 이 중 가장 비싸다.** 인프라 전체보다 GPU 하나가 더
비싸므로, 시연 직전에 켜고 끝나면 `modal app stop`으로 내리는 습관이 필요하다.

**프로젝트가 끝나면 NAT Gateway를 반드시 삭제할 것.** 인스턴스를 정지해도 이건 계속
과금된다. 방치해서 몇 달 뒤 요금이 쌓이는 것이 가장 흔한 사고다.

## 7. 구축 순서

1. **VPC 생성** — 10.0.0.0/16
2. **서브넷 5개** — 위 표대로
3. **Internet Gateway** 연결, 퍼블릭 서브넷 라우팅 테이블에 `0.0.0.0/0 → IGW`
4. **NAT Gateway** (public-a) 생성, 프라이빗 라우팅 테이블에 `0.0.0.0/0 → NAT`
5. **S3 Gateway Endpoint** 생성, 프라이빗 라우팅 테이블에 연결
6. **보안그룹 3개** — 위 표대로. **서로를 참조하도록**
7. **RDS 서브넷 그룹** (private-db-a, private-db-c) → RDS 생성
8. **EC2 2대** — nginx(public-a), 앱(private-app-a)
9. 앱 서버에 Docker 설치 → 레포 clone → `.env` 작성 → `docker compose up -d`
10. nginx 서버에 `deploy/nginx.conf` 배치, `upstream`을 앱 서버 **사설 IP**로 수정
11. Twilio 전화번호 Webhook을 실제 도메인으로 변경

**프라이빗 서브넷의 앱 서버에는 SSH로 직접 못 들어간다.** nginx 서버를 경유하거나
(SSH 터널) AWS Systems Manager Session Manager를 쓴다. 후자가 22번을 아예 안 열어도
되므로 더 낫다.

## 8. 검증 후 정리 (중요)

이 프로젝트는 **한 번 올려서 동작을 확인하고 캡처한 뒤 곧바로 내리는 것**이 전제다.
그때 "중지"로는 부족하다. 중지해도 계속 과금되는 것이 있다.

| 자원 | 중지하면 | 실제 |
|---|---|---|
| EC2 인스턴스 | 과금 0 | 정지로 충분 |
| **EBS 볼륨** | 계속 과금 | 60GB ≈ 월 $5.5. 인스턴스를 terminate해야 같이 사라진다 |
| **NAT Gateway** | 중지 자체가 없다 | 월 ~$35. **삭제만이 방법** |
| **탄력적 IP / 공인 IPv4** | 계속 과금 | 개당 월 ~$3.6 |
| **RDS** | 스토리지 계속 | 게다가 **7일 뒤 자동 재시작**된다 |

### 삭제 순서

```
1. modal app stop qwen3-asr-streaming   ← 제일 비싸다(시간당 ~$1.1). 가장 먼저
2. EC2 2대            terminate  (stop이 아니라 terminate)
3. RDS                삭제. 최종 스냅샷은 건너뛴다(스냅샷도 과금)
4. NAT Gateway        삭제      ← 빠뜨리기 가장 쉽고 가장 비싸다
5. 탄력적 IP          할당 해제
6. EBS 볼륨           terminate로 같이 지워졌는지 확인
```

### 남겨도 되는 것 (무료)

**VPC, 서브넷, 라우팅 테이블, 인터넷 게이트웨이, 보안그룹, S3 Gateway Endpoint는
만들어 두는 것만으로는 과금되지 않는다.** 별첨에 넣을 구조도 캡처는 이것들로 충분하므로
지우지 않고 계정에 그대로 두어도 된다.

즉 **무료 구조를 먼저 만들어 캡처 → 유료 자원(NAT·EC2·RDS)을 잠깐 켜서 동작 확인 및
캡처 → 유료 자원만 삭제** 순서가 가장 싸다. 3~4시간이면 $2~3 수준이다.

## 9. 아직 해결되지 않은 것

배포 전에 판단이 필요한 항목이다.

| 항목 | 상태 | 영향 |
|---|---|---|
| **HTTPS** | 미적용 | JWT와 상담 원문이 평문으로 오간다. 도메인 + Let's Encrypt 필요 |
| **Twilio 서명 검증** | 미구현 | `/webhook`을 아무나 호출할 수 있다 |
| `.env` 평문 보관 | 서버 디스크에 | `PII_ENCRYPTION_KEY`가 새면 DB 전체가 복호화된다. Secrets Manager 검토 |
| AWS 키 주입 방식 | 환경변수 | EC2라면 **IAM 역할**이 맞다. 키를 파일에 두지 않아도 된다 |
| DB 백업 | 없음 | RDS 자동 백업 켜기 |
| 단일 AZ | 의도된 제약 | 상태를 Redis로 빼기 전까지는 확장 불가 |

**HTTPS와 Twilio 서명 검증 둘은 실제 상담 데이터를 넣기 전 필수다.**
